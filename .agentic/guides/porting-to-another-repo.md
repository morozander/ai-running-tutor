# Porting the spec-driven workflow to another repo

Hand this guide + the files below to a team adopting the workflow in a different
codebase (any architecture: monorepo or single-package, any stack, Claude Code or
Cursor). The workflow splits cleanly into a **portable kernel** (state machine,
skills, subagents, hooks, verification gates) and a **project layer** (your rules,
your commands, your package names). You copy the kernel, replace the project layer,
and adjust four stack-heavy files.

## What to copy — the share manifest

| Path | Action |
|---|---|
| `.claude/skills/` (workflow kernel) | **copy, then adjust** — the ticket-flow skills (`work`, `start`, `plan`, `implement-plan`, `verify`, `open-mr`, plus standalone `brainstorm`/`debug`/`explore`/`lint-ticket`/`using-workflow`). Package names + a few stack commands (see checklist) |
| `.claude/skills/` (engineering / Matt) | **optional** — `/ask-matt` flow (`grill-*`, `to-spec`, `to-tickets`, `implement`, `handoff`, `triage`, `tdd`, …) plus `.claude/commands/` and `docs/agents/`; skip if you only want the Jira ticket workflow |
| `.claude/agents/` (all 13) | **copy, then adjust** — 2 verifier files carry most stack coupling |
| `.claude/hooks/` (5 scripts) | **copy as-is** — dual-format (Claude Code + Cursor), repo-agnostic; teams without IaC simply never trigger the IaC rule |
| `.claude/settings.json` | **copy, then adjust** — keep hooks/plugins/marketplace blocks; rewrite the `permissions.allow` command list for your package manager |
| `.claude/ONBOARDING.md` | **copy as template** — rewrite prerequisites/examples for your stack |
| `.cursor/hooks.json`, `.cursor/settings.json` | **copy as-is** |
| `.cursor/cli.json` | **copy, then adjust** — allow-list to your package manager; keep/extend the deny-list |
| `.cursor/mcp.json` + root `.mcp.json` | **copy, then adjust** — your Jira env; drop servers you don't use (e.g. aws-mcp) |
| `.cursor/README.md` | **copy as-is** (generic layout doc) |
| `.agentic/scripts/` (sync.ts + package.json + tsconfig) | **copy, then adjust** — `PACKAGE_SYMLINKS` to your package layout; `CURSOR_MODEL_MAP` if you want different tiers |
| `.agentic/guides/` (ba-ticket-authoring, designer-handoff, this file) | **copy as template** — rewrite examples for your product |
| `.agentic/rules/**`, `.agentic/packages/*`, `.agentic/AGENTS.md` | **REPLACE entirely** — this is YOUR standards content (see step 3) |

## Adjustment checklist (in order)

1. **Package vocabulary sweep.** Skills/agents reference our packages (`backend/`,
   `frontend/`, `mobile/`, `iaac/`, ~90 mentions). Find/replace with your layout.
   Single-package repo: collapse to your one package — the verify wave's
   "affected packages" logic handles it naturally, and design-parity declares
   itself `not-applicable` for non-UI work already.
2. **Stack-command surface — 4 files carry ~80% of it.** Rewrite build/test/run
   commands in: `agents/build-check-verifier.md`, `agents/runtime-smoke-verifier.md`
   (drop the Expo/simulator sections if no mobile), `skills/implement/SKILL.md`
   (the migration-create command), `agents/task-implementer.md`. Then a light grep
   sweep for `pnpm |expo |terragrunt|simctl|adb ` across the rest (single-digit
   mentions each).
3. **Author your project layer** — the real work. `.agentic/rules/<category>/*.md`
   (your coding standards, mined from your existing style guides / exemplar code),
   `.agentic/packages/<pkg>.md` (per-package ambient context), `.agentic/AGENTS.md`
   (repo overview — keep our section structure). Then `cd .agentic/scripts && pnpm
   install && pnpm sync` to generate `.cursor/rules` + `.cursor/agents` + symlinks.
4. **Permissions allowlists** (`.claude/settings.json`, `.cursor/cli.json`) — swap
   `pnpm …` entries for your package manager; keep git entries. Extend the deny-list
   with YOUR dangerous commands (`kubectl apply`, prod DB scripts, …) — the IaC-apply
   ban pattern in `pre-tool-use.sh` is the template.
5. **MCP wiring.** Jira: the internal-jira MCP works for any team on the org Jira —
   each dev supplies their own `JIRA_BASE_URL`/`JIRA_PAT` via the setup script.
   Figma: OAuth per dev. Remember env-var syntax differs between the twin files
   (`${VAR}` in `.mcp.json`, `${env:VAR}` in `.cursor/mcp.json`).
6. **Ticket-key examples** are cosmetic (`PROJ-123` style); extraction is
   pattern-based from branch names (`feat/KEY-123`) and works for any Jira project
   key. Just update examples in docs if you care.

## Hard dependencies — know before adopting

- **Jira is required.** `/start` refuses without a ticket; the DoR gate and the
  BA input contract are the point of the flow. No Jira → this workflow isn't for
  that team (or budget ~a day to swap the tracker MCP + `/start`'s fetch section).
- **Figma is required for UI tickets.** Teams with no Figma: edit `/start`'s
  design-completeness check + design-parity dispatch to honor a declared
  `design_source: none` mode (~1 hour, the one code-level change we haven't
  needed). Backend-only teams: nothing to do — design-parity already no-ops.
- **A dev-loop that runs locally.** runtime-smoke boots your app and screenshots
  it; if your app can't run locally (hard cloud deps), that verifier degrades to
  build-check only — decide whether that's acceptable before adopting.

## Effort estimate

- Similar stack (TS/web): **~half a day** for checklist items 1–2 + 4–6.
- Different ecosystem (JVM/Python/Go): **1–2 days** — same items, plus rethinking
  the build/test command surface in the 4 stack-heavy files.
- Item 3 (authoring YOUR rules) is the real investment: hours if you have written
  standards to convert, days if you're mining them from the codebase. It is also
  where the workflow's quality comes from — don't skip it.

## End-state (when a second team adopts)

Once this port has been done twice, extract the kernel into an installable
**plugin** (both Claude Code and Cursor support bundles of skills + agents +
hooks) parameterized by a per-repo manifest (packages, commands, tracker, design
source). Until then, copy-and-adjust is simpler than premature abstraction.
