# /handoff — MR/PR Opening

Called by `/work` when state phase is `review-ready`. Detects the remote (GitLab vs GitHub) and opens the request using the right CLI.

## Model strategy

| Component | Subagent | Model |
|---|---|---|
| Compose MR/PR body | `handoff-writer` | haiku |

Templated text generation; no judgment needed. Haiku is correct here.

## Inputs

- State at `.claude/state/<TICKET>.json`
- Plan at `.agentic/plans/<TICKET>/plan.md`
- Verifier reports at `.agentic/plans/<TICKET>/verify/*.json`
- Branch with all commits
- **Canary token** for this pass — `CANARY-<random-word>-<4 digits>`, generated by the `/work` driver and passed in (see "Canary + evidence protocol")

## Canary + evidence protocol (per pass)

The `/work` driver generates ONE canary token per pass — `CANARY-<random-word>-<4 digits>` — and
passes it to this skill. Inject it **verbatim** into the handoff-writer dispatch. The handoff-writer
MUST echo the canary verbatim in its return — a missing/altered canary means the return is suspect
→ **re-dispatch**.

The handoff-writer returns a machine-checkable `evidence` block: the artifact path it wrote
(`.agentic/plans/<TICKET>/handoff.md`) and exact counts copied from its own reading (tasks covered,
verifier reports read). It composes templated text and does not navigate code, so `lsp` is not
applicable. Numbers must be COPIED from real output, never estimated.

**RE-CHECK the evidence (the teeth).** Confirm `handoff.md` exists before opening the MR/PR; after
opening, confirm the returned MR/PR URL actually resolves (`gh pr view` / `glab mr view`) — a URL
that doesn't resolve is a `hallucination_flag`, never reported as opened. Confirm the pushed branch
HEAD SHA exists (`git cat-file -e $(git rev-parse HEAD)`). A missing/altered canary → re-dispatch.

## Procedure

### 1. Detect remote

```bash
remote_url=$(git remote get-url origin)
case "$remote_url" in
  *gitlab*)    PLATFORM=gitlab;    CLI=glab ;;
  *github*)    PLATFORM=github;    CLI=gh ;;
  *bitbucket*) PLATFORM=bitbucket; CLI=manual ;;
  *)           PLATFORM=unknown;   CLI=manual ;;
esac
```

If no `origin` configured:

```
⚠ No git remote configured. Cannot open MR/PR.
   Have me compose the MR description anyway (you push manually later)?
```

If CLI not installed, prompt to install or pick manual mode.

Also read the base branch the feature was cut from — use `state.base_branch`, defaulting to `main` if absent. This is the branch the MR/PR must target (do NOT hardcode `main`):

```bash
BASE_BRANCH=$(jq -r '.base_branch // "main"' .claude/state/<TICKET>.json)
```

### 2. Push the branch

```bash
git push -u origin "$BRANCH"
```

If rejected (protected target, rebase needed), surface the error verbatim.

### 3. Dispatch handoff-writer (haiku)

```
Task(
  subagent_type: "handoff-writer",
  prompt: "Compose MR/PR title + description for <TICKET>.

           Plan: .agentic/plans/<TICKET>/plan.md
           Verifier reports: .agentic/plans/<TICKET>/verify/*.json
           Platform: <gitlab|github|bitbucket>

           Output to .agentic/plans/<TICKET>/handoff.md.
           Follow .claude/agents/handoff-writer.md template.

           CANARY: echo this token verbatim in your return — <CANARY>.
           EVIDENCE: return an `evidence` block — the handoff.md path written + exact counts
           (tasks covered, verifier reports read), copied from real output, never estimated."
)
```

The writer produces:

- Title: `<type>(<scope>): <summary> [<TICKET>]`
- Body with: Summary, Changes (per task), AC coverage table, Verification summary, **Deployment Prerequisites** (any `environment` or `iaac` tasks), Out of Scope, Test plan

### 3b. Archive the spec (spec-anchoring — the plan must survive the merge)

`.agentic/plans/*` is gitignored (per-dev, ephemeral), so without this step the spec that produced
the code disappears after merge — spec-driven, but not spec-anchored. Anchor it:

```bash
mkdir -p docs/specs/<TICKET>
cp .agentic/plans/<TICKET>/plan.md                 docs/specs/<TICKET>/plan.md
cp .agentic/plans/<TICKET>/verify/coordinator.json docs/specs/<TICKET>/coordinator.json  # if it exists
cp .agentic/plans/<TICKET>/handoff.md              docs/specs/<TICKET>/handoff.md
git add docs/specs/<TICKET> && git commit -m "docs(<TICKET>): archive plan + verification verdict" && git push
```

On a `--skip-verify` run there is no `coordinator.json` — archive what exists (the missing verdict is
itself part of the record). The archive rides the same MR, so the reviewer sees the spec AND the
verification verdict next to the diff, and post-merge spec-vs-code drift stays checkable from git
history alone.

### 4. Open the MR/PR

Read `.agentic/plans/<TICKET>/handoff.md` and split into title + body.

**GitLab**:
```bash
glab mr create \
  --target-branch "$BASE_BRANCH" \
  --title "$TITLE" \
  --description "$BODY" \
  --label "spec-driven-workflow" \
  --label "ticket:<TICKET>" \
  --remove-source-branch \
  --squash-before-merge
```

**GitHub**:
```bash
gh pr create \
  --base "$BASE_BRANCH" \
  --title "$TITLE" \
  --body "$BODY" \
  --label "spec-driven-workflow"
```

Capture the URL.

**RE-CHECK (teeth):** confirm the captured URL actually resolves (`gh pr view <URL>` /
`glab mr view <URL>`) before reporting it opened — a URL that doesn't resolve is a
`hallucination_flag`, never reported as opened. Confirm the pushed branch HEAD SHA exists
(`git cat-file -e $(git rev-parse HEAD)`).

### 5. Update the Jira ticket (if write tools available)

Once `internal-jira-mcp` v0.2+ ships `jira_add_comment` and `jira_transition`:

The verification block lists one line per verifier in the `/verify` roster — `verify/SKILL.md` is the single source for the verifier set; derive the lines from it, don't hardcode the list (the body below is a worked example for the current roster):

```
internal-jira.jira_add_comment(
  key: "<TICKET>",
  body: "MR opened: <URL>

         Verification:
         - QA: ✓
         - Code review: ✓
         - Security: ✓ (or 'N findings resolved')
         - Build check: ✓
         - Runtime smoke: ✓ (or '⚠ inconclusive — <reason>')
         - Design parity: ✓ (or 'not-applicable — non-UI ticket')"
)

internal-jira.jira_transition(key: "<TICKET>", transition: "In Review")
```

If those tools don't exist yet, print the comment body + instruct dev to add manually.

### 6. Update state

Via the locked write path (never a whole-JSON write — see `work/SKILL.md` §4):

```bash
node .claude/scripts/state-update.mjs "$state_file" set phase=done mr_url=<URL>
node .claude/scripts/state-update.mjs "$state_file" append-history --summary "MR opened at <URL>"
#   ↳ ts + duration_s are stamped automatically
```

`/handoff` surfaces its OWN `evidence` block to the driver + final message: the pushed HEAD SHA
(`git rev-parse HEAD`), the commit count on the branch, the MR/PR URL (verified to resolve), and
the `handoff.md` path — every value COPIED from real command output, never estimated.

### 7. Final message to dev

```
✓ MR opened: <URL>

Next:
  • Request review from a teammate
  • Once approved + CI green, merge with squash

⚠ Deployment prerequisites (derive from THIS ticket's plan — its environment/iaac tasks
  + any runtime-smoke human_blocker; the items below are an illustrative example for a
  "Sign in with Apple" ticket, not a fixed list):
  □ *(e.g.)* Apple Developer App ID: enable Sign in with Apple capability
  □ *(e.g.)* Apply iaac/.../cognito/ changes after MR merges (task t8)
  □ *(e.g.)* Cognito app client: add Apple to allowed providers

Ticket <TICKET> is now `done` in this workflow. Run /work TICKET-NEW to start the next one.
```

## Edge cases

### No verifier reports

If `.agentic/plans/<TICKET>/verify/` is empty:

```
✗ No verification reports found.
   /handoff requires verifier reports. Run /verify first.
   (Or use /handoff --skip-verify if you're sure — adds skip-verify label.)
```

### `--skip-verify` flag

Allowed but discouraged. MR gets an extra `skip-verify` label and body includes:
```
⚠ Verification skipped at submitter's request.
```

### CI fails immediately

If `glab ci status` / `gh pr checks` shows failures within first minute, surface them but don't try to fix from `/handoff` — that's a separate concern.

### Push rejected (rebase needed)

```
✗ Push rejected: target branch updated since you branched.
   Rebase onto the base branch (state.base_branch, default main):
     git fetch origin
     git rebase origin/<base_branch>
   Resolve conflicts, then continue.
```

Wait for dev to handle.

## Hard rules

- ❌ Opening MR/PR with no commits
- ❌ Skipping the §3b spec archive — the MR must carry `docs/specs/<TICKET>/` (plan + verdict); the gitignored plan dir is not a durable record
- ❌ Skipping verifier reports without `--skip-verify`
- ❌ Force-pushing to a protected target
- ❌ Closing the previous MR for the same ticket — link them instead
- ❌ Hardcoding GitLab assumptions — always detect remote
- ❌ Including secret references in MR body
- ❌ Implementing environment-task code into the branch — those go in Deployment Prerequisites only
- ❌ Reporting an MR/PR URL as opened without confirming it resolves (`gh pr view` / `glab mr view`) — an unresolvable URL is a `hallucination_flag`
- ❌ Trusting a handoff-writer return whose canary is missing/altered — re-dispatch
