# /implement-plan — Task Execution

Called by `/work` when state phase is `implementing` (or `fixing`). Runs one task at a time using a fresh `task-implementer` subagent for each.

## Model strategy

| Component | Subagent | Model |
|---|---|---|
| Per-task implementer (one call per task) | `task-implementer` | sonnet |
| Fix-mode implementer (per finding) | `task-implementer` | sonnet |

Sonnet handles code generation in a TDD loop well at ~1/5 the cost of Opus. The plan is already detailed by the planner + plan-reviewer, so the implementer's job is mostly mechanical translation.

## Inputs

- State at `.claude/state/<TICKET>.json`
- Plan at `.agentic/plans/<TICKET>/plan.md`
- Optional verifier feedback when in fix-mode
- **Canary token** for this pass — `CANARY-<random-word>-<4 digits>`, generated by the `/work` driver and passed in (see "Canary + evidence protocol")
- **Execution mode** — `CONSTRAINED` | `AMPLE`, from the driver's one-time host-RAM probe (see "Execution mode")

## Execution mode — RAM-aware (CONSTRAINED vs AMPLE)

The `/work` driver probes host RAM ONCE at pass start (total GB + free%) and records the mode in
state — **CONSTRAINED** (total ≤ ~18GB) vs **AMPLE**. `/implement-plan` reads that mode; it does NOT
re-probe.

- **CONSTRAINED mode:** ONE task-implementer / spawn at a time — never fan out fix-mode dispatches
  concurrently; every node command capped `NODE_OPTIONS=--max-old-space-size=1536`; `jest
  --maxWorkers=2`; a **cooldown gate** between heavy steps — wait until free mem ≥ ~45% before the
  next spawn / build / migration-up; boot/bundle steps one at a time; prefer delegate-then-ground-truth
  over parallel fan-out.
- **AMPLE mode:** unchanged — the existing flow.

This is a MODE branch, not a rewrite: the task order, TDD loop, validation checks, and gates are
identical; only serial-vs-concurrent spawning + the node/jest caps differ.

## Canary + evidence protocol (per pass)

The `/work` driver generates ONE canary token per pass — `CANARY-<random-word>-<4 digits>` — and
passes it to this skill. Inject it **verbatim** into EVERY task-implementer dispatch (normal,
migration, and fix-mode). Every subagent MUST echo the canary verbatim in its return — a
missing/altered canary means the return is suspect → **re-dispatch** (do not trust it).

Every task-implementer MUST return a machine-checkable `evidence` block:

- commit SHA(s) it created (from `git rev-parse HEAD` / the commit hash),
- exact counts copied from its own command output (tests passed/failed, build exit code, files changed),
- artifact paths,
- `lsp: { calls: <int>, usedFor: [<short strings>] }` (validated per the LSP enforcement rule).

Numbers must be COPIED from real command output, never estimated. The evidence re-check (the teeth)
runs in the validation step (§5); `/implement-plan` surfaces its OWN aggregate `evidence` block to the
driver on return (§8).

## Procedure — normal mode

### 1. Pick the next task

Read the plan, identify the next task by `state.current_task` and the DAG. **Foundation tasks first** (the plan ordering already enforces this; double-check).

If no tasks remain:
```
state.phase = "implementing" → "verifying"
return — driver calls /verify next
```

### 2. Skip environment tasks

If task `type` is `environment` — **do NOT implement**. These flow to `/open-mr`'s "Deployment Prerequisites" section. Mark as `skipped_for_handoff` in state and continue to the next task.

```bash
if task.type == "environment":
  node .claude/scripts/state-update.mjs "$state_file" append-history \
    --summary "task <task.id> deferred-to-handoff (environment task)"
  pick next task
```

### 3. Dispatch task-implementer (sonnet)

For task types `code`, `foundation`, `iaac` — standard implement flow.

**Pass the task's FULL declared context inline.** Every dispatch must inline the task's
complete `context_files` + `references` (not a summary, not a pointer to "see the plan").
The subagent runs in a fresh context with no memory of prior tasks — if a file or reference
isn't passed here, the implementer cannot see it.

```
Task(
  subagent_type: "task-implementer",
  prompt: "Implement task <task.id> from .agentic/plans/<TICKET>/plan.md.

           Mode: normal
           Task type: <task.type>
           Context files (load ONLY these — full declared list inline): <task.context_files>
           Files to modify: <task.files_to_modify>
           Files to create: <task.files_to_create>
           Acceptance: <task.acceptance>
           References (full declared list inline): <task.references>

           TOOLCHAIN: run EVERY install/build/test/migration under the pinned
           toolchain via 'mise exec --' (the versions pinned in mise.toml) — NEVER
           bare pnpm/npx. Installs use '--frozen-lockfile'.

           Follow .claude/agents/task-implementer.md.
           TDD enforced via superpowers:test-driven-development.
           After completion: git status MUST show changes ONLY in the declared file lists.

           RAM MODE: <CONSTRAINED|AMPLE>. If CONSTRAINED, cap every node command with
           NODE_OPTIONS=--max-old-space-size=1536 and run jest with --maxWorkers=2.

           CANARY: echo this token verbatim in your return — <CANARY>.
           EVIDENCE: return a machine-checkable `evidence` block — commit SHA(s) created
           (from `git rev-parse HEAD`), exact counts copied from real output (tests
           passed/failed, build exit code, files changed), artifact paths, and
           `lsp: { calls, usedFor }`. Numbers COPIED from command output, never estimated."
)
```

> **TOOLCHAIN DISCIPLINE.** Every install / build / test / migration command — in this
> skill and in every task-implementer dispatch — runs under the pinned toolchain via
> `mise exec -- <cmd>` (the versions pinned in `mise.toml` — e.g. (THIS repo): node 22.22.0 /
> pnpm 9.15.0). Installs use `--frozen-lockfile`. NEVER invoke bare `pnpm`/`npx`.
> WHEN a toolchain-managed install/build fails under the pinned runner, DIAGNOSE the actual
> error first — the pin makes "wrong node/pnpm version" unlikely by construction, so read the
> failure itself. WHEN a failure "goes away" only by leaving the pinned toolchain (a bare
> package manager, a different node/runner), that is masking the dependency state, not fixing
> it — **forbidden**. (e.g. a past run: a failing `expo install` was "fixed" with a bare
> `pnpm install`, which produced a broken Metro bundle plus a masked missing dep.)

> **STATE OWNERSHIP.** Only the `/work` driver writes `.claude/state/<TICKET>.json`.
> The task-implementer subagent MUST NEVER write or edit state files. If a task-implementer
> reports the context-expansion escape hatch (`need additional context`), this skill does
> **NOT** let it guess: PAUSE the task, route back to re-plan / augment the task's
> `context_files` + `references`, then re-dispatch with the expanded context inline.

### 4. Special handling — migration tasks

If task `type` is `migration`:

```
Task(
  subagent_type: "task-implementer",
  prompt: "Migration task <task.id>: <task.title>.

           Context files (full declared list inline): <task.context_files>
           References (full declared list inline): <task.references>

           TOOLCHAIN: every command below runs under the pinned toolchain via
           'mise exec --' (the versions pinned in mise.toml) — NEVER bare pnpm/npx.

           Procedure:
           1. Apply the entity changes in <task.files_to_modify>
           2. cd backend && run the migration-create script defined in
              backend/package.json (e.g. (THIS repo): mise exec -- pnpm db:migrate:create)
           3. Verify the generated migration file under the migrations dir configured
              in mikro-orm.config.ts (e.g. (THIS repo): backend/src/core/database/migrations/)
              matches the expected schema diff
           4. The migration-up + tests below need the database service. Check the
              runtime ledger (.agentic/plans/<TICKET>/verify/runtime-ledger.json) and
              what's running (docker ps) FIRST — reuse a running DB. Start it ONLY if
              absent (e.g. (THIS repo): mise run docker-up), append it to the ledger
              with its teardown one-liner (per-SERVICE: `docker compose stop <svc> && docker compose rm -f <svc>` — NOT `mise run docker-down`, which removes ALL compose services incl. ones you did not start), and LEAVE IT UP —
              never stop a service you didn't start.
              (Per .agentic/rules/_shared/leave-no-trace.md.)
           5. cd backend && run the migration-up script (e.g. (THIS repo):
              mise exec -- pnpm db:migrate:up) to apply locally
           6. Run backend tests (under mise exec --) to confirm DB layer still works
           7. Commit entity changes + generated migration in one commit

           Do NOT hand-write the migration SQL. See .agentic/rules/backend/migrations.md.
           If the migration-create script produces unexpected output (e.g., empty migration,
           drops you didn't intend), STOP and report — don't apply.

           RAM MODE: <CONSTRAINED|AMPLE>. If CONSTRAINED, cap every node command with
           NODE_OPTIONS=--max-old-space-size=1536 and run jest with --maxWorkers=2.

           CANARY: echo this token verbatim in your return — <CANARY>.
           EVIDENCE: return a machine-checkable `evidence` block — commit SHA(s) created
           (from `git rev-parse HEAD`), exact counts copied from real output (tests
           passed/failed, build exit code, files changed), artifact paths, and
           `lsp: { calls, usedFor }`. Numbers COPIED from command output, never estimated."
)
```

> **Services the task needs (per `.agentic/rules/_shared/leave-no-trace.md`).** The
> service-lifecycle instruction MUST live in the dispatch prompt above (and in
> `task-implementer.md`) — the implementer runs in a fresh context and never reads this
> skill body. The shape: reuse a running DB; start it only if absent, ledgering it in
> `.agentic/plans/<TICKET>/verify/runtime-ledger.json` with its teardown one-liner; leave
> it up across the remaining tasks AND the verify phase (they reuse it — stopping between
> tasks just re-pays the boot). Disposition belongs to /verify and the /work driver at
> phase/run end. Never stop a service the flow didn't start.

### 5. Validate the subagent's output

The subagent returns a **concise structured result** — status + key findings + files changed +
a 1–3 line summary + a pointer to any report file — NOT a full narration/transcript of every
edit. Validate against that structured result (and `git status`); do not expect a replayed log.

All commands below run under the pinned toolchain via `mise exec --` — NEVER bare `pnpm`/`npx`.

| Check | How |
|---|---|
| File scope | `git status` shows changes ONLY in declared `files_to_modify + files_to_create` |
| Tests | Run the package test command (under `mise exec --`) for the affected files; must pass |
| Typecheck | `mise exec -- pnpm typecheck` (or `mise exec -- tsc --noEmit`) in the package |
| Lint | `mise exec -- pnpm check` (Biome) or `mise exec -- pnpm lint` |

**Evidence + canary re-check (the teeth).** First confirm the subagent echoed the canary
verbatim — a missing/altered canary means the return is suspect → **re-dispatch**. Then
independently re-check its `evidence` block: `git cat-file -e <sha>` for each claimed commit;
cross-check a reported count against a spot re-run (e.g. re-run the affected test file); confirm
each claimed artifact path exists. A claimed SHA that doesn't exist, or a count that contradicts
the re-check → a `hallucination_flag` finding → the task is re-done or ESCALATED, never trusted.
If the diff touched `.ts/.tsx` with cross-file symbol navigation but `lsp.calls` is 0, treat it
as a `process_gap` per the LSP enforcement rule.

If any check fails, re-dispatch with the failure as additional input. **Cap: 2 retries per task** before surfacing to dev.

### 6. Commit was made by the subagent

The `task-implementer` commits the task itself per `.claude/agents/task-implementer.md`. Verify the commit exists:

```bash
git log -1 --pretty=%s   # should reference the task
```

### 7. Update state

Via the locked write path (never a whole-JSON write — see `work/SKILL.md` §4):

```bash
node .claude/scripts/state-update.mjs "$state_file" set current_task=<next-task-id-or-null>
node .claude/scripts/state-update.mjs "$state_file" append-history --summary "Completed t1: ..."
#   ↳ ts + duration_s are stamped automatically; the post-tool-use hook has already
#     appended the per-commit entries through the same path
```

### 8. Loop or advance

- Tasks remain → repeat from step 1 in the SAME `/work` invocation (continuous execution per `/work` SKILL.md)
- All tasks done → set phase to `verifying`, return to driver

On return, `/implement-plan` surfaces its OWN machine-checkable `evidence` block to the driver: the
per-task commit SHA(s) it re-checked (`git cat-file -e`), aggregate counts (tasks completed,
tests passed/failed, files changed), and the plan/report artifact paths — every number COPIED
from real command output, never estimated. The driver re-checks this sample in turn.

## Procedure — fix-mode

When called by driver because `/verify` found fixable issues.

### 1. Load verifier coordinator decision

State has `state.verify_findings` populated by coordinator's routing:

```json
{
  "fix_routing": [
    {
      "target_task": "t3",
      "fixes": [
        { "file": "...", "issue": "...", "suggested_fix": "..." }
      ]
    },
    {
      "target_task": "t1",
      "fixes": [...]
    }
  ]
}
```

### 2. Dispatch ONE task-implementer per fix-target (BATCH the fixes)

For each entry in `fix_routing`, dispatch a **single** implementer in fix-mode that carries
**all** of that target task's fixes at once. The fixes for one target share context (same task,
overlapping files) — do NOT spawn a separate implementer per individual finding. One target
task = one fix dispatch carrying the whole batch.

```
Task(
  subagent_type: "task-implementer",
  prompt: "Fix-mode for task <target_task>.

           Apply this BATCH of fixes (the full set for this task, and ONLY these):
           <ALL fixes for this target_task, each with file + issue + suggested_fix>

           Constraints:
           - Modify ONLY the files listed in fixes
           - Re-run failing tests to confirm fixes
           - Do NOT introduce new tasks or expand scope
           - Either amend the previous task commit (if it's HEAD and fix is small)
             or create a new fix commit
           - Return a CONCISE structured result (status + key findings + files changed +
             1–3 line summary + pointer to any report file), NOT a full transcript.

           RAM MODE: <CONSTRAINED|AMPLE>. If CONSTRAINED, cap every node command with
           NODE_OPTIONS=--max-old-space-size=1536 and run jest with --maxWorkers=2.

           CANARY: echo this token verbatim in your return — <CANARY>.
           EVIDENCE: return a machine-checkable `evidence` block — commit SHA(s) created
           (from `git rev-parse HEAD`), exact counts copied from real output (tests
           passed/failed, build exit code, files changed), artifact paths, and
           `lsp: { calls, usedFor }`. Numbers COPIED from command output, never estimated."
)
```

Under **CONSTRAINED mode**, dispatch these per-target fix implementers **sequentially** — one at a
time with the cooldown gate between them (free mem ≥ ~45%) — never concurrently. Under AMPLE mode
the existing dispatch cadence is unchanged.

**BUDGET — increment on every fix dispatch.** Each fix-mode dispatch (one per target task)
increments the tracked counter:

```
state.iterations.fix_dispatches += 1   // one increment per fix-target dispatch
```

`state.iterations` is owned by the `/work` driver (see STATE OWNERSHIP — this skill never
writes state directly; it reports the increment to the driver, which persists it). When the
driver's `max_verify_loops` ceiling (default 3) is exceeded, ESCALATE for dev approval rather
than continuing to dispatch fixes.

### 3. Validate (same checks as normal mode)

### 4. Update state + hand back to driver

```
state.phase = "fixing" → "verifying"
state.verify_findings = null
```

Driver re-runs `/verify`.

## Budget guard — trackable iteration ceiling

There is **no enforced $-budget** (the workflow can't read real dollars, so a prose "$X budget"
could never actually fire). Instead the budget is a **trackable iteration ceiling** kept in
`state.iterations`:

```json
"iterations": { "verify_loops": <n>, "fix_dispatches": <n> }
```

- Each fix-mode dispatch increments `state.iterations.fix_dispatches` (see fix-mode step 2).
- The `/work` driver owns and persists `state.iterations` and enforces `max_verify_loops`
  (default **3**). When the ceiling is exceeded, the driver/coordinator **ESCALATE for dev
  approval** before any further fix dispatch — they do not silently keep looping.

```
⚠ Verify/fix ceiling reached: verify_loops=3 (max_verify_loops=3), fix_dispatches=N.
   Approve more iterations?  abort?  re-scope?
```

An approximate $-estimate MAY be shown alongside, but ONLY clearly labelled as a rough estimate
(e.g. "≈ $X, rough estimate") — never presented as an enforced budget. Wait for dev reply in chat.

## When to escalate

Stop and ask the dev when:

- Required files don't exist (plan is wrong)
- TDD red phase reveals the AC is impossible without scope expansion
- The subagent retries twice without converging
- The iteration ceiling is exceeded (`state.iterations` vs `max_verify_loops`, default 3) — escalate for dev approval
- The task-implementer reports the context-expansion escape hatch (`need additional context`)
  — PAUSE the task; do NOT let the implementer guess. Route back to re-plan / augment the
  task's `context_files` + `references`, then re-dispatch with the expanded context inline.

## Hard rules

- ❌ Loading files outside the task's `context_files`
- ❌ Skipping TDD — every functional change starts with a failing test
- ❌ Modifying files outside the task's declared lists without dev approval
- ❌ Force-pushing or rebasing during implementation — preserve history
- ❌ Marking a task complete with failing tests
- ❌ Cross-task contamination — one subagent context per task, fresh each time
- ❌ Hand-writing migrations — always generate via the migration-create script defined in `backend/package.json` (e.g. (THIS repo): `mise exec -- pnpm db:migrate:create`)
- ❌ Implementing `type: environment` tasks — those go to `/open-mr`
- ❌ Bare `pnpm`/`npx` for any install/build/test/migration — always `mise exec --`, installs `--frozen-lockfile`
- ❌ Making an install/build failure "go away" by leaving the pinned toolchain (e.g. a failing `expo install` → bare `pnpm install`) — that masks the dependency state; diagnose the actual error and fix it
- ❌ A subagent writing/editing `.claude/state/<TICKET>.json` — only the `/work` driver owns state
- ❌ Letting a task-implementer guess when it reports `need additional context` — PAUSE and route back to re-plan / augment context
- ❌ Trusting a subagent return whose canary is missing/altered — re-dispatch; the return is suspect
- ❌ Trusting a claimed commit SHA or count without re-check — `git cat-file -e <sha>` + spot cross-check; a non-existent SHA or a contradicted count is a `hallucination_flag`
- ❌ (CONSTRAINED mode) fanning out concurrent spawns or running uncapped node — one spawn at a time, `NODE_OPTIONS=--max-old-space-size=1536`, `jest --maxWorkers=2`, cooldown to ≥ ~45% free between heavy steps
- ❌ Starting a long-lived service without appending it to the ticket runtime ledger (`.agentic/plans/<TICKET>/verify/runtime-ledger.json`) — and never stopping a service the flow didn't start (per `.agentic/rules/_shared/leave-no-trace.md`)
